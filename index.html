A task runner for people
who write code,
not configuration.

birun is what happens when you stop pretending that YAML is a programming language. You describe your tasks in bi — a small, honest scripting language with real conditionals, real loops, and real functions. Then birun runs them quickly, correctly, and with caching that doesn't lie to you.

$ curl -fsSL https://raw.githubusercontent.com/barshansarkar/birun/main/install.sh | sh
Install guide Star on GitHub

Why birun exists

Every project grows a weird little script. First it's one file. Six lines. Someone adds a flag, someone else adds a dependency, and by month three you have a directory named scripts/ with fourteen files, each one sourcing the last.

So the sensible teams migrate. They move to Makefile and discover tabs. They move to package.json scripts and discover that a JSON file has become their build system. They move to just or task and discover that everything is fine until someone needs an if.

"Can we skip the deploy on a dry run?"
"Can we only run the linter if the config changed?"
"Can we build for arm64 when we're on CI but x86_64 locally?"

Every time, the answer is the same: bolt on another script. Write the condition in shell. Repeat yourself in three places. The build system, once again, becomes a small private language that nobody else can read.

birun is a different answer. Not "let's add a plugin." Not "let's write it in JavaScript." The answer is: what if the build system had a language, and the language was small enough that everyone could learn it in an afternoon?

That language is bi. It has variables. It has if and else. It has for loops. It has functions and closures. It has arrays and maps. And that is all it has. Everything else — the shell commands, the file checks, the environment reads — you already know.

Pick whichever method fits your workflow.

01 One-liner (Linux/macOS)

Detects your OS and architecture, downloads the correct binary, verifies the checksum.

curl -fsSL https://raw.githubusercontent.com/barshansarkar/birun/main/install.sh | sh

02 Download from Releases

Get the tarball for your platform directly. Verify with the accompanying .sha256 file.

linux-aarch64 194 KB

darwin-arm64 194 KB

Open Releases page

03 Build from source

Requires CMake 3.16+ and any C++17 compiler. Builds in ~90 seconds.

git clone https://github.com/barshansarkar/birun
cd birun
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
sudo cmake --install build

04 Cross-compile Windows from Linux

Produces a self-contained static .exe — no MinGW runtime DLLs needed.

sudo apt install mingw-w64
cmake -S . -B build-win \
  -DCMAKE_SYSTEM_NAME=Windows \
  -DCMAKE_CXX_COMPILER=x86_64-w64-mingw32-g++ \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build-win -j
Verify: After install, run birun --version. It should print birun 1.0.0.

Full example

A real config — complete enough to ship to CI.

// birun.bi

let mgr      = pkg()          // detect: cargo / npm / pip / go / ...
let isCI     = inCI()
let isDarwin = (os() == "darwin")
let isWin    = (os() == "windows")

route TASK "/hello" {
    desc("Say hello")
    run("echo 'hello from birun'")
}

route TASK "/build" {
    desc("Compile the project")
    depends("hello")
    inputs("src/**/*.rs", "Cargo.toml")
    outputs("target/release/app")
    timeout(180)
    retry(2, 500)
    env("RUST_BACKTRACE", "1")

    if (mgr == "cargo") {
        run("cargo build --release")
    } else if (mgr == "npm") {
        run("npm run build")
    } else {
        run("echo 'no build system detected'")
    }
}

route TASK "/test" {
    desc("Run the test suite")
    depends("build")
    timeout(300)
    run("cargo test")
}

route TASK "/fetch" {
    desc("Fetch remote metadata (flaky)")
    timeout(30)
    retry(3, 500)
    env("HTTP_TIMEOUT", "10")
    run("curl -f https://flaky.example.com/meta")
}

route TASK "/clean" {
    desc("Remove build artifacts")
    if (isWin) {
        run("if exist target rmdir /s /q target")
    } else {
        run("rm -rf target dist build")
    }
}

route TASK "/ci" {
    desc("Full CI pipeline")
    depends("build", "test")
    if (isCI) {
        run("echo 'CI mode: extra strict checks'")
        run("cargo clippy -- -D warnings")
    }
}

route TASK "/release" {
    desc("Tag and push a release")
    depends("ci")
    run("git tag v$(cat VERSION)")
    run("git push --tags")
}

Run it: birun -j4 ci, birun --watch test, birun --stats all.

The birun.bi format

A single file. Real code. No schema.

birun.bi is loaded and executed on every run. It's parsed by bi, a small tree-walking interpreter embedded in the birun binary. It's fast enough that parsing is invisible — a thousand-line config loads before your finger leaves Enter.

Tasks are registered by route TASK "/name" { ... }. The task's body runs during config load and calls builtins (run, desc, inputs, ...) that register metadata on the current task. Once all routes are executed, birun has a full task graph.

Anything else in the file — let bindings, function definitions, conditionals at the top level, loops — runs during config load and can be referenced from within any task.

Tip: Because the config is real code, you can generate tasks dynamically with loops: 
for (t in ["web", "api", "worker"]) {
    route TASK "/build-" + t {
        desc("Build " + t)
        run("make " + t)
    }
}

The bi language

Small enough to learn in fifteen minutes. Powerful enough for real logic.

Variables

let name    = "world"
let count   = 42
let pi      = 3.14159
let enabled = true
let items   = [1, 2, 3]
let config  = { host: "localhost", port: 8080 }

Functions

fn greet(who) {
    return "hello, " + who
}

let msg = greet("birun")   // "hello, birun"

Conditionals

let mgr = pkg()
if (mgr == "cargo") {
    print("rust project")
} else if (mgr == "npm") {
    print("node project")
} else {
    print("unknown")
}

Loops

for (let i = 0; i < 5; i++) {
    print(i)
}

for (name in ["a", "b", "c"]) {
    print(name)
}

Imports, try/catch

import "./helpers.bi" as h

try {
    sh("might-fail")
} catch (err) {
    print("caught: " + err)
}

Task builtins

Only valid inside a route TASK { ... } block. They register metadata on the current task.

desc(text) metadata

Human-readable description. Shown in --list, in --json, and in the plan output.

desc("Compile the release binary")
depends("a", "b") graph

Declares dependencies. Also accepts a single array: depends(["a", "b"]). birun computes the correct order from these edges. Cycles are detected and reported.

depends("build", "lint")
run(cmd) command

Adds a shell command. Multiple run() calls execute in order. Each runs in its own process group, so signals propagate to the whole tree.

run("cargo build --release")
run("strip target/release/app")
inputs("src/*.cpp") cache

Glob patterns for cache inputs. Supports *, ?, and ** (recursive). Multiple patterns accepted. Content of every matched file is hashed.

inputs("src/**/*.cpp", "include/**/*.h")
outputs("build/app") cache

Files this task is expected to produce. A cache hit requires all outputs to exist. If any is missing, the task reruns.

outputs("target/release/app")
timeout(sec) control

Kill the task's commands after N seconds. SIGTERM to the process group, wait --grace, then SIGKILL. Exit code 124.

timeout(180)
retry(n, backoffMs) control

Retry the entire task up to n+1 times on failure. Backoff doubles each attempt (500ms → 1s → 2s → ...), capped at 30s. Retries stop if cancellation or shutdown is requested.

retry(3, 500)
env("KEY", "VALUE") context

Set an environment variable for this task's child processes. Multiple env() calls accumulate. Note: inside a task, env("K", "V") sets; outside, env("K") reads.

env("RUST_BACKTRACE", "1")
env("NODE_OPTIONS", "--max-old-space-size=4096")
cwd("path") context

Run the task's commands from this directory. The child process calls chdir() before exec.

cwd("./frontend")

System builtins

Available anywhere — top level, inside tasks, inside functions.

Command execution

sh(cmd)

Run, capture stdout. Throws on non-zero exit. Trailing newline is trimmed.

sh(cmd, strict)

With strict=false, non-zero exit does not throw — output is returned.

shStatus(cmd)

Run silently, return only the exit code as int. 124 on timeout.

shFull(cmd)

Returns a map: {code, out, err, timedOut}. On Windows, out and err are merged (documented limitation).

Filesystem

which(tool)

Full path to an executable on PATH, or null. On Windows, checks .exe, .bat, .cmd, .com, .ps1.

exists(path)

Returns bool. Works on files and directories.

glob(pattern)

Expand a glob to a sorted array of paths. Supports *, ?, **.

cwd()

Current working directory as string. Inside a task, cwd("path") sets instead.

System

os()

"linux", "darwin", "windows", or "unknown".

arch()

"x86_64", "arm64", "x86", "arm", or "unknown".

inCI()

True if CI or CONTINUOUS_INTEGRATION is set and not "false".

env("X")

Read env var. Returns null if unset. With default: env("X", "default").

pkg()

Package manager detection. Returns "pnpm", "yarn", "bun", "npm", "cargo", "uv", "poetry", "pip", "go", "composer", "maven", "gradle", "bundler", "mix", "pub", or null.

Core builtins

print(x) — print to stdout with newline

len(x) — length of string, array, or map

str(x), num(x), int(x), bool(x) — type conversion

type(x) — returns the type name as string

upper(s), lower(s), trim(s) — string helpers

range(n) — generate array of integers

time() — current Unix time as number

Caching

Content hashes, not timestamps. Versioned format. Concurrent-safe.

Make uses file modification times. That means a fresh git clone looks "newer" than the build output it shipped with — everything rebuilds for nothing. And if you restore an old file from backup, Make quietly skips the rebuild you actually needed.

birun hashes the contents of every file matching your inputs(), along with the task's full definition. If a single byte changed, the task reruns. If nothing changed, it doesn't.

What goes into the hash

  • → Every run() command, in order
  • → desc(), depends(), outputs()
  • → env()
    cwd() timeout() retry() retryBackoffMs
  • → Content hash (FNV-1a 64) of every matched input file
  • → BIRUN_CACHE_MAGIC version string

Cache location and format

Default: .birun/cache. Override via BIRUN_CACHE_FILE. The file begins with a magic header line (birun-cache-v2) followed by tab-separated key\tvalue lines.

Cache invalidation across versions

When birun upgrades and BIRUN_CACHE_FORMAT changes, old cache files are silently discarded on the next run. No manual --clean needed. Your CI keeps working across birun upgrades.

Concurrency safety

Cache writes take an advisory file lock — flock() on POSIX, LockFileEx on Windows. The lock is acquired with exponential backoff (~775 ms total across 5 attempts). If the lock cannot be acquired, birun throws rather than silently overwriting — a lost update is worse than a failed write.

Atomic writes

All cache writes go to a temp file in the same directory, then rename(). On POSIX, rename is atomic. On Windows, fs::rename uses the appropriate primitive. A crash mid-write cannot leave a corrupted cache.

Glob support: * matches within a segment. ? matches a single character. ** matches recursively. Patterns are expanded at both cache-computation time and output-verification time.

Parallelism

Real threads. First-failure-wins. No orphans.

birun -j8 all runs up to eight independent tasks at once. The scheduler reads the dependency graph, keeps a queue of ready tasks, and dispatches to a thread pool.

Dependency ordering

A task only becomes eligible once all its depends() have completed successfully. This is computed once at start and updated as tasks finish.

First-failure cancel

When a task fails, birun calls proc::requestCancel(). That sends SIGTERM to every registered child process tree (POSIX) or terminates the Job Object (Windows). Workers see the cancel flag and drain. The grace period then escalates any stragglers to SIGKILL.

The first failure determines the final exit code. Later failures caused by cancellation (exit 130) do not overwrite it. This is enforced with a compare-and-swap — no race, no ambiguity.

Buffered output

Each task's stdout is captured privately and written when the task completes. Two parallel tasks never confuse each other's output — you get the speed of concurrency without the garbled terminal that comes from plain &.

Watch mode

Save file, watch task run. Event-driven on Linux.

$ birun --watch test
  ⚡ change detected · 2 file(s)
      • src/main.rs
      • Cargo.toml
  ✓ build   2.41s
  ✓ test    0.82s

How it works

  1. 1. Take a snapshot of all tracked files (path → mtime)
  2. 2. Wait for events — inotify on Linux, polling fallback elsewhere
  3. 3. Debounce: wait 300 ms for writes to settle
  4. 4. Re-diff; if anything changed, re-run
  5. 5. Auto-reload birun.bi if the config changed

Ignore filter

These directories are never watched:

.git/ .hg/ .svn/ build/ dist/ node_modules/ target/ __pycache__/ .venv/ .idea/ .vscode/ .next/

Watched extensions

Only source-like files trigger re-runs — image writes, binary drops, etc. are ignored. Extensions include .bi, .sh, .c, .cpp, .h, .rs, .go, .py, .js, .ts, .json, .yaml, .toml, and more.

Error recovery

If you save a syntactically invalid birun.bi, birun prints the parse error with file:line:col and keeps watching. A bad save does not kill the session.

Timeouts & retries

Real builds fail in real ways. Every task declares its own policy.

route TASK "/fetch" {
    timeout(30)           // SIGTERM → grace → SIGKILL
    retry(3, 500)         // 500ms → 1s → 2s backoff
    env("HTTP_TIMEOUT", "10")
    cwd("./vendor")
    run("curl -f https://flaky.example.com/meta")
}

Timeout

On timeout, birun sends SIGTERM to the process group first, waits --grace seconds (default 3), then sends SIGKILL. The task exits with code 124. On Windows, GenerateConsoleCtrlEvent is tried first, then TerminateProcess.

Because every child is in its own process group, grandchild processes are killed too — no orphaned cargo or node processes holding ports.

Retry

retry(n, backoffMs) retries the entire task up to n+1 times. Backoff doubles each attempt: backoffMs * 2^(attempt-1), capped at 30 seconds.

The retry wraps all of a task's run() commands. If a task has three commands and the third fails, all three run again on retry. Retries stop immediately if cancellation or shutdown is requested — a failing sibling won't wait out a full backoff.

Grace period

Configurable via --grace N (0-60 seconds, default 3). Applies to task timeouts, task cancellation, and SIGINT/SIGTERM shutdown. A second signal skips the grace period entirely and goes straight to SIGKILL.

Path separators

Both / and \ work in glob patterns. Use whichever is more readable.

Console colors

birun enables UTF-8 code page and ANSI escape processing on Windows 10+. If colors look odd on older consoles, set NO_COLOR=1 or BIRUN_ASCII=1.

Known limitations (Windows): Watch mode uses polling (not ReadDirectoryChangesW yet). shFull() merges stdout and stderr — the POSIX version keeps them split. Both are documented roadmap items.

Architecture

Small, layered, no dependencies beyond libc and C++17.

src/
├── main.cpp              CLI, argument parsing, orchestration
├── executor.{hpp,cpp}    Task DAG, sequential + parallel execution
├── cache.hpp             Input hashing, cache store, glob expansion
├── builtins_birun.hpp    Task + system builtins for `bi`
├── extras.hpp            JSON, Graphviz, completion, --init
├── theme.hpp             Colors, symbols, formatting
├── watch.hpp             File watching (inotify + polling)
├── version.hpp           Version + cache format constants
├── proc.hpp              Dispatcher: POSIX or Windows
└── platform/
    ├── proc_posix.hpp    fork/exec, process groups, signals
    ├── proc_win32.hpp    CreateProcess, Job Objects
    └── fslock.hpp        Cross-platform file lock

Design decisions

  • → No dependencies beyond C++17 standard library. One CMakeLists.txt, one build.
  • → No system(). Always fork/exec or CreateProcess.
  • → Signal handlers use only lock-free atomics, guarded by static_assert.
  • → Cache versioning — format changes invalidate old caches.
  • → First-failure-wins — CAS semantics ensure the original error survives cancellation.
  • → Async-signal-safe — no printf, malloc, or locks in signal context.
  • → Zero warnings under -Wall -Wextra on GCC, Clang, MSVC, MinGW.

Robustness

The unglamorous parts that matter most.

No orphaned processes

Every child is placed in its own process group. On SIGINT, birun sends SIGTERM to the entire group, waits the grace period, then SIGKILLs anything left. On Windows, all children are assigned to a single Job Object — closing it kills the whole tree atomically.

Async-signal-safe handlers

  • → Signal handlers touch only lock-free std::atomic operations. All non-signal-safe work — process cleanup, child reaping — happens on a dedicated reaper thread.
  • → static_assert(std::atomic<T>::is_always_lock_free) guarantees it at compile time.

Correct error reporting

Parse errors include file, line, and column. Runtime errors carry a stack trace. Task failures include the exit code and the failing command. No silent failures.

No cache corruption

Writes go to a temp file in the same directory, then rename(). On POSIX, rename is atomic — a crash mid-write cannot leave a corrupt cache. Concurrent writes are serialized through a file lock with retry.

Never silent overwrite

If the cache lock cannot be acquired after 5 retries (~775 ms), birun throws. It does not silently overwrite a locked cache. A lost update is worse than a failed write.

birun is a fit if

  • — You want real logic in your build, not templating
  • — You want caching that survives branch switches and CI restores
  • — You want per-task timeouts, retries, env, cwd without wrapping every command
  • — You want one static binary, no runtime, no package manager

birun is not a fit if

  • — You need remote shared caching for a large monorepo
  • — You want the most battle-hardened option available
  • — You'd rather not learn another small language
  • — You need deeply nested configuration inheritance

FAQ

Why not just use Make?

Make is 48 years old and still excellent at what it does. It is also a macro language pretending to be a build system, and its timestamp-based caching is wrong more often than people realize.

If your build is a small DAG of file-to-file transformations, Make is fine. If your build involves conditionals, environment detection, orchestration of external tools, or anything you would call "logic," the Makefile becomes harder to read than the shell script you started with.

Is the caching actually correct?

We hash the content of every file matching your inputs(), plus the task's full definition. If any of those change, the cache invalidates.

The one case where we cannot be certain: a task depends on something we can't see — a remote service, a file outside declared inputs, wall-clock time. That's not a bug in birun; it's a bug in the task definition. True of every caching build system.

What happens if a task hangs?

Add timeout(30) to the task. Any command that exceeds 30s is killed — SIGTERM to the process group, wait --grace, then SIGKILL. Exit code 124.

Add retry(3, 500) and the whole task runs up to four times with exponential backoff. Transient network failures, rate-limited APIs, and eventually-consistent services stop being your problem.

What is bi, really?

A small tree-walking interpreter written in about 1,500 lines of C++. Two dozen syntax forms. No classes, no exceptions to speak of, no module system beyond file imports, no standard library beyond a fixed set of builtins that birun registers.

The design philosophy: do not grow. Every feature added to a build language is a feature everyone using that language has to learn. If a feature can be expressed with what exists, it does not belong.

Is Windows really supported?

Yes, natively — not through WSL. Windows uses CreateProcess and Job Objects. The release binary is a static .exe with no external DLL dependencies. CI runs the full test suite on windows-latest.

Windows is marked experimental because it has less real-world mileage than Linux/macOS. Field reports are welcome.

Can the cache be shared across a team?

Not yet. The cache is a local file at .birun/cache. You can commit it or sync it via CI artifacts — the hash keys are deterministic across machines. But there is no cache server, no S3 backend, no HTTP protocol.

Concurrent local runs are safe — cache writes take an advisory file lock with retry.

Is it production-ready?

For personal and small-team use: yes. 64 tests run on every push across Ubuntu, macOS, and Windows. Zero warnings under -Wall -Wextra. Five platform binaries ship with every release, each with a SHA256 checksum.

For large production infrastructure with shared caching needs: still wait. Remote caching and signed binaries are on the roadmap.
