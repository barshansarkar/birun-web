v0.6.2 — quietly building in the corner

A task runner for people
who write code,
not configuration.

birun is what happens when you stop pretending that YAML is a programming language. You describe your tasks in bi — a small, honest scripting language with real conditionals, real loops, and real functions. Then birun runs them quickly, correctly, and with caching that doesn't lie to you.

Chapter one

Every project grows
a weird little script.

First it's one file. run.sh. Six lines. Someone adds a flag, someone else adds a dependency, and by month three you have a directory named scripts/ with fourteen files, each one sourcing the last, each one half-broken, none of them documented. Anyone who wants to run the tests has to read a shell script to figure out which one is the "real" one.

So the sensible teams migrate. They move to Makefile and discover tabs. They move to package.json scripts and discover that a JSON file has become their build system. They move to just or task and discover that everything is fine until someone needs an if.

"Can we skip the deploy on a dry run?"
"Can we only run the linter if the config changed?"
"Can we build for arm64 when we're on CI but x86_64 locally?"

And every time, the answer is the same. You bolt on another script. You write the condition in shell. You repeat yourself in three places. The build system, once again, becomes a small private language that nobody else can read.

birun is a different answer to that question. Not "let's add a plugin." Not "let's write it in JavaScript." Not "let's embed Python and hope." The answer is: what if the build system had a language, and the language was small enough that everyone could learn it in an afternoon?

That language is bi. It has variables. It has if and else. It has for loops, both C-style and for-in. It has functions and closures. It has arrays and maps. And that is all it has. There is no module system to learn, no standard library to memorize, no package registry to argue about. Everything else — the shell commands, the file checks, the environment reads — you already know.

A build file should read like a recipe, not like a contract. It should tell you what it does when you look at it, not what it might do after seven layers of inheritance.

birun is not the first tool to think this. mage said it — but only if you already write Go. mask said it — but Markdown is not a language, it's a mood. birun's bet is simpler: a small purpose-built language is worth more than a large general-purpose one for the specific job of describing build steps.

That's it. That's the whole story. If it resonates with you, the rest of this page tells you what birun actually does and how it differs from the tools you might already know. If it doesn't, that's fine too — make still works, and it always will.

Three tasks. One of them cached.

The third task didn't run because its inputs — and its own definition — hadn't changed. That is the whole idea: if nothing moved, nothing runs.

Chapter two

What's actually inside.

Every feature below exists because a real build broke without it. Nothing here is aspirational — it all ships in the binary you downloaded two minutes ago.

01 — Language

A tiny language that respects your time.

bi is small on purpose. Variables, conditionals, loops, functions, arrays, maps. If you have written JavaScript or Python for a week, you can read it fluently. If you have never written either, you can learn the whole language in fifteen minutes.

It compiles to nothing — it's interpreted directly from your birun.bi file each run, so there is no build step to your build step. The parse is fast enough to be invisible; even a thousand-line config loads before your finger leaves the Enter key.

02 — Caching

Content hashes, not timestamps.

Make uses file modification times. That means a fresh git clone looks "newer" than the build output it shipped with, and everything rebuilds for no reason. It also means that if you restore an old file from backup, Make will quietly skip the rebuild you actually needed.

birun hashes the contents of every file you list in inputs(), along with the task's own definition — its commands, its description, its dependencies. If a single byte changed, the task reruns. If nothing changed, it doesn't. Simple and honest.

Result: Switch branches, check out old commits, restore from backup — cache stays correct.
03 — Parallelism

Real threads. Real speedup.

birun reads your dependency graph, works out which tasks are ready, and runs them on a thread pool. -j8 means eight tasks running at once, not eight tasks queued on one worker.

Each task's output is buffered privately and written atomically when the task finishes, so two parallel tasks never confuse each other's stdout. You get the speed of concurrency without the garbled terminal you'd get from plain &.

04 — Watch

Save file, watch task run.

birun --watch test polls your project for changes and re-runs the moment something moves. It skips the obvious noise: .git, node_modules, target, build, .venv, __pycache__. And it only watches extensions that could plausibly matter — no rebuild trigger from a stray .log file.

Rapid saves are debounced. If your editor writes three files in fifty milliseconds, you get one build, not three. If your config becomes syntactically invalid, birun prints the error and keeps watching — a broken save doesn't kill your session.

05 — Distribution

One file. No runtime.

birun is a single statically-linked C++ binary. Around two hundred kilobytes stripped. It has no dependency on Node, Python, the JVM, or a system package manager. It runs on any Linux from the last decade and any macOS since Catalina.

That matters more than it sounds. Every tool that requires a runtime has to justify the runtime's cost. birun doesn't. You curl it once, put it in your PATH, and it exists — on your laptop, on the build server, in a container that only has sh and coreutils, anywhere.

Getting it

Install in a single line.

The one-liner below downloads the correct binary for your platform, verifies it, and puts it in ~/.local/bin. If that directory isn't already on your PATH, it tells you how to add it.

01

Linux and macOS

Works on x86_64 and aarch64 for both platforms. The script picks the right build automatically.

curl -fsSL https://raw.githubusercontent.com/barshansarkar/birun/main/install.sh | sh
02

Build from source

Requires CMake 3.16+ and any C++17 compiler. Takes about ninety seconds on a modern laptop. 

git clone https://github.com/barshansarkar/birun
cd birun
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
sudo cmake --install build

Then check

$ birun --version
birun 0.6.2

Chapter three

From an empty folder
to a working pipeline.

The rest of this section walks through a real configuration — small enough to read in one sitting, complete enough to ship to CI.

01

Start a new project file.

birun --init writes a small birun.bi into the current directory. It contains four example tasks you can delete or keep. There is no hidden state, no lock file, no metadata directory — just one file you own.

$ birun --init
created birun.bi
$ ls
birun.bi
02

Describe your tasks.

A task is declared with route TASK "/name" { ... }. Inside the block you call builtins that describe what the task is. The block is real code, so anything that computes — if, for, function calls — works exactly as you would expect. 

let mgr  = pkg()
let isCI = inCI()

route TASK "/build" {
    desc("Compile the project")
    inputs("src/**/*.rs", "Cargo.toml")
    outputs("target/release/app")

    if (mgr == "cargo") {
        run("cargo build --release")
    } else if (mgr == "npm") {
        run("npm run build")
    } else {
        run("echo 'no build system detected'")
    }

    if (isCI) {
        run("echo 'running in CI mode'")
    }
}

route TASK "/test" {
    desc("Run the test suite")
    depends("build")
    run("cargo test")
}

Note the second task only names one thing — it depends on build. birun figures out the correct order from that. You never write the sequence by hand.

03

Look before you leap.

--dry-run shows what would run without executing anything. --verbose prints the reason each task ran or was skipped. Use them together when you're trying to figure out why a cache is or isn't hitting. 

$ birun --dry-run test
  ⚡ would execute 2 task(s)
   1  ○ build   Compile the project
   2  ○ test    Run the test suite

$ birun --verbose build
  ⚡ plan · 1 task(s) · jobs=1 · cache=on
  ✓ cache hit b31dc6a95a43
  ✓ build   cached
04

Watch, then walk away.

For the inner development loop, --watch is the difference between context-switching every thirty seconds and staying in flow. Save your file, look at the terminal, see the result. That's the whole interaction. 

$ birun --watch test
  ⚡ change detected · 2 file(s)
      • src/main.rs
      • Cargo.toml
  ✓ build   2.41s
  ✓ test    0.82s
05

Drop it into CI.

The install line works inside any runner. Because birun is quiet when it succeeds and loud when it fails, you can pass --quiet and get a CI log that only has content when something is wrong. 

# .github/workflows/build.yml
- name: Install birun
  run: curl -fsSL https://raw.githubusercontent.com/barshansarkar/birun/main/install.sh | sh

- name: Run CI
  run: ~/.local/bin/birun -j4 --quiet ci

Reference

The complete command set.

Fifteen flags total. That number is not a coincidence — every one earns its place, or it would have been cut.

Command
Purpose
birun <task>
Run the task and everything it depends on.
-l, --list
Print every task, with descriptions and dependencies.
-n, --dry-run
Show the plan without executing any command.
-j, --jobs N
Run up to N tasks in parallel. -j 4 and -j4 both work.
-w, --watch
Re-run whenever a tracked file changes. Ctrl-C to stop.

Never read from or write to the cache file.

Ignore cache hits for this run, but still refresh the cache afterward.

Delete the cache file. Combine with a task name to clean then run.

Chapter four

Where it sits in the world.

Every tool below is worth using. The comparison is not "birun is better" — it's "birun is different, and here is exactly how."

Tool Config format Cache Logic Runtime
birun birun.bi content-hash full language none
GNU Make Makefile timestamps macro only sh
just justfile none limited sh
go-task Taskfile.yml checksum templating none
mage magefile.go none Go code Go
mask maskfile.md none none sh
turbo turbo.json remote JSON Node

birun is a fit if

  • — You want real logic in your build steps, not templating
  • — You want caching that survives branch switches and CI restores
  • — You like single-binary tools that don't drag in a runtime
  • — You already write shell and want something that reads better

birun is not a fit if

  • — You need Windows support today. It's planned, not shipped.
  • — You want remote shared caching for a large monorepo. Use turbo.
  • — You want the most battle-hardened option available. Use Make.
  • — You'd rather not learn another small language, even a tiny one.

Objections

The questions people ask.

Why not just use Make?

Make is forty-eight years old and still excellent at what it does. It is also a macro language pretending to be a build system, and its timestamp-based caching is wrong more often than people realize.

If your build is a small DAG of file-to-file transformations, Make is perfectly fine. If your build involves conditionals, environment detection, orchestration of external tools, or anything you would call "logic", the Makefile becomes harder to read than the shell script you started with. birun is for that second case.

Is the caching actually correct?

We hash the content of every file matching your inputs() globs, along with the task's own definition — every run() command, its description, its dependency list, its outputs. If any of those change, the cache invalidates. If none do, the task skips.

The one case where we cannot be certain is when a task's behavior depends on something we can't see — a remote service, a file outside your declared inputs, the current time. That is not a bug in birun; it is a bug in the task definition. If your task reads from /etc/hosts and you did not declare that as an input, the cache will happily serve a stale result. This is true of every caching build system.

What is bi, really?

bi is a small tree-walking interpreter written in about 1,500 lines of C++. It has two dozen syntax forms. It has no classes, no exceptions to speak of, no module system beyond file imports, and no standard library beyond a fixed set of builtins that birun registers.

The design philosophy is: do not grow. Every feature that gets added to a build language is a feature that everyone using that language has to learn. If a feature can be expressed with what exists, it does not belong in the language. This is why there will never be a "bi 2.0 with generics."

What about Windows?

Planned. Not shipped. The blocker is not C++ — it is that birun's executor shells out to popen and reads waitpid, both of which are POSIX. Windows support requires abstracting that layer behind a small process API, and then testing the whole thing on a platform none of the current contributors use daily.

We would rather say "not yet" honestly than ship a Windows port that does something subtly wrong. If you are on Windows and want to help, the executor abstraction is a well-scoped first contribution.

Can the cache be shared across a team?

Not yet. The cache is a local file at .birun/cache. You can commit it or sync it via CI artifacts, and it will work — the hash keys are deterministic across machines. But there is no cache server, no S3 backend, no HTTP protocol for retrieving remote entries.

Remote caching is on the roadmap, but only after the local model is proven against many real projects. It is easy to build a remote cache. It is hard to build one that never serves a wrong result.

Is it production-ready?

Depends what you mean. The core is solid — the executor, cache, and parser all have tests, and the tool has been benchmarked against real workloads. It is currently at version 0.6.2, which in semantic versioning means "API may still change."

For personal projects and small teams: yes, today. For large production infrastructure: probably wait for 1.0. We would rather underpromise and ship slowly than call something production-ready before it has earned the word.
